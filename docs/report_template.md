Отчёт по проекту LocalHub
1. Цель работы
Целью работы являлась разработка настольного приложения LocalHub на языке Python, предназначенного для обмена данными между пользователями в локальной сети. Приложение реализует собственный HTTP-клиент и собственный HTTP-сервер на низкоуровневых сокетах, без использования готовых сетевых фреймворков (Flask, FastAPI, http.server, requests, urllib, http.client, aiohttp, httpx и т. п.). Дополнительно реализован графический интерфейс (GUI) на [tkinter / PyQt — указать фактический], обеспечивающий работу с клиентом, сервером и общими файлами, а также набор unit- и интеграционных тестов.

Задачи работы:

спроектировать ООП-архитектуру с разделением на транспорт, парсинг, бизнес-логику и GUI;

реализовать HTTP-клиент с поддержкой методов GET и POST, разбором URL, таймаутами и обработкой ошибок;

реализовать многопоточный HTTP-сервер с маршрутизацией и корректной остановкой;

реализовать GUI, не блокирующийся во время сетевых операций;

обеспечить базовую безопасность (лимиты, валидация, защита от path traversal);

покрыть ключевые модули тестами и прогнать линтеры.

2. Функциональные возможности
Приложение состоит из трёх вкладок: Client, Server, Shared Files.

Вкладка Client позволяет:

вводить URL и выбирать метод GET или POST;

редактировать заголовки запроса (таблица «ключ — значение»);

вводить тело запроса (многострочное поле, активно для POST);

отправлять запрос и просматривать статус-код, заголовки и тело ответа;

видеть сообщения об ошибках (некорректный URL, таймаут, отказ соединения).

Вкладка Server позволяет:

задавать порт (с валидацией диапазона 1–65535) и запускать/останавливать сервер;

просматривать таблицу лога запросов (время, метод, путь, статус, IP клиента, размер ответа);

просматривать детали последнего запроса/ответа.

Назначение ключевых классов:

Transport — инкапсулирует работу с сокетом: connect, send, recv, close; реализован как контекстный менеджер (RAII), чтобы сокет закрывался даже при исключении.

RequestHandler — обрабатывает одно клиентское соединение на сервере: читает запрос, вызывает Router, формирует и отправляет ответ, корректно завершает соединение с учётом Connection: close / keep-alive.

HttpClient — формирует HTTP-запрос, отправляет его через Transport, читает и разбирает ответ, поддерживает таймауты, выбрасывает собственные исключения.

HttpServer — владеет слушающим сокетом, выполняет bind/listen/accept, принимает соединения в отдельном потоке и на каждое соединение запускает поток с RequestHandler, обеспечивает корректную остановку.

Router — хранит отображение «путь/шаблон → Callable-обработчик», разбирает параметры пути (например, {code} в /status/{code}), возвращает 404 при отсутствии совпадения.

LocalHubHandler — набор обработчиков бизнес-логики для маршрутов LocalHub (/hello, /echo, /time, /headers, /status/{code}, файловые маршруты).

4. Работа HTTP-клиента
Разбор URL. Класс Url (url.py) разбирает строку вида http://host:8080/path?q=1 на схему, хост, порт, путь и query-параметры. Если порт не указан, подставляется порт по умолчанию (80 для http, 443 для https). Некорректный URL приводит к исключению UrlParseError.

Установка TCP-соединения. HttpClient создаёт сокет через Transport, устанавливает таймаут (socket.settimeout), выполняет connect((host, port)). Сокет используется в контекстном менеджере (with), что гарантирует закрытие.

Сериализация запроса. Формируется request-line (METHOD path?query HTTP/1.1), заголовок Host, пользовательские заголовки, при необходимости Content-Length и тело. Строки кодируются в байты (UTF-8), разделитель — \r\n.

Чтение и разбор ответа. Сначала читаются заголовки до \r\n\r\n, затем тело: по Content-Length, либо по Transfer-Encoding: chunked (чтение чанков до чанка размера 0), либо до закрытия соединения. Статус-строка и заголовки разбираются парсером.

Таймауты и исключения. Используются таймауты на connect/recv; при ошибках выбрасываются ConnectionError, TimeoutError, InvalidResponseError, HttpProtocolError. Сетевые операции выполняются в фоновом потоке, результат передаётся в GUI через queue.Queue, чтобы не блокировать интерфейс.

5. Работа HTTP-сервера
Сервер создаёт сокет, выставляет SO_REUSEADDR, выполняет bind и listen(backlog). Приём соединений (accept) выполняется в отдельном потоке приёма, чтобы не блокировать GUI и главный поток. На каждое принятое соединение запускается отдельный поток с RequestHandler, что даёт многопоточную обработку клиентов.

RequestHandler читает запрос (request-line, заголовки, тело с учётом Content-Length/chunked), передаёт его в Router, получает Response и сериализует ответ: статус-строка, заголовки (Content-Type, Content-Length, Connection, Date, Server), тело.

Заголовок Connection обрабатывается явно: при close соединение закрывается после ответа, при keep-alive — сохраняется с таймаутом для следующего запроса. Некорректные запросы приводят к ответу 400 Bad Request (или 413/431 при превышении лимитов), исключение перехватывается на уровне обработчика соединения, сервер не падает.

Остановка сервера выполняется корректно: закрывается слушающий сокет, потоки дожидаются завершения (join с таймаутом), порт освобождается, GUI обновляется (кнопка Start снова активна).

6. GUI и многопоточность
GUI-фреймворки не потокобезопасны, поэтому обновление виджетов выполняется только из главного потока. Фоновые потоки (клиентские запросы, приём соединений, обработка соединений) не обращаются к виджетам напрямую, а кладут результат в queue.Queue. Главный поток периодически (через root.after(...) для tkinter или через сигналы/слоты для PyQt) забирает данные из очереди и обновляет интерфейс. Это обеспечивает отзывчивость GUI и отсутствие гонок.

7. Безопасность
Лимит заголовков 8 КБ — при превышении запрос отклоняется (ответ 431/400), сервер не читает бесконечно заголовки.

Лимит тела 10 МБ — при превышении запрос отклоняется (ответ 413), что защищает от переполнения памяти.

Валидация порта — целое число в диапазоне 1–65535; при неверном вводе кнопка Start блокируется и/или выводится сообщение.

Обработка некорректного HTTP — мусор вместо request-line, неверные заголовки и т. п. приводят к ответу 400 и не роняют сервер.

Защита имени файла от path traversal — имя нормализуется, итоговый абсолютный путь проверяется на принадлежность корневой директории (например, через Path.resolve() и is_relative_to(root)); попытки выйти через ../ отклоняются.
